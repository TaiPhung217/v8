Descriptionvm...@google.com created issue #1

Project Fortify, an experimental security project, has identified the following potential security issue.

Overview: Chrome's experimental Signature-based Subresource Integrity (SRI) implementation skips resource body verification when the Unencoded-Digest header uses unsupported hash algorithms (e.g., sha-384). This allows an attacker to bypass SRI by modifying the resource body while leaving the legitimately signed headers intact.

Affected files:

services/network/public/cpp/unencoded_digests.cc
third_party/blink/renderer/platform/loader/subresource_integrity.cc
services/network/public/cpp/sri_message_signatures.cc
Estimated timestamp from git blame: 2025-07-31

Vulnerability Summary
A logic error in Chrome's experimental Signature-based Subresource Integrity (SRI) implementation leads to a "fail-open" scenario when a resource is served with a signed Unencoded-Digest header containing unrecognized hash algorithms.

Although the browser successfully validates the Ed25519 signature over the response headers, it fails to perform any integrity check on the resource body if it cannot extract a supported digest (currently only SHA-256 and SHA-512 are supported). This allows an on-path attacker or compromised CDN to replace the resource body with arbitrary malicious code, bypassing the security guarantees of SRI.

Technical Analysis
Signature Base Construction (services/network/public/cpp/sri_message_signatures.cc): During signature verification, Chrome constructs a signature base that includes the Unencoded-Digest header. The code (lines 743-752) serializes the dictionary into the base without validating whether the hash algorithms specified within the header are actually supported. Thus, a signature over a header like Unencoded-Digest: sha-384=:<digest>: passes Ed25519 verification if legitimately signed by the origin.

Digest Extraction (services/network/public/cpp/unencoded_digests.cc): The extraction logic (ParseUnencodedDigestsFromHeaders, lines 48-84) only recognizes sha-256 and sha-512. If the header contains other algorithms, such as sha-384 or misspelled keys, the parser skips them using continue (line 63). The resulting digests vector is empty.

Fail-Open Body Verification (third_party/blink/renderer/platform/loader/subresource_integrity.cc): The Blink-side verification function SubresourceIntegrity::CheckUnencodedDigests (lines 174-201) iterates over the digests vector. Because the vector is empty, the loop does not execute, and the function returns true, indicating success. The body goes completely unverified.

Signature Verification (third_party/blink/renderer/platform/loader/subresource_integrity.cc): Finally, Blink verifies the signatures in CheckSignaturesImpl (lines 332-391) by ensuring a parsed signature has a keyid matching the expected public key from the <script> tag. Because the attacker left the headers untouched, this check passes.

Suggested Exploitation Steps (Theoretical)
Note: These are potential steps as we have not verified them with a working exploit.

A developer implements Signature-based SRI: <script integrity="ed25519-<pubkey>" src="https://cdn.example.com/script.js"></script>.
The legitimate origin server serves the script with an Unencoded-Digest header using an unsupported algorithm, such as sha-384, and correctly signs it.
Unencoded-Digest: sha-384=:<valid_sha384_digest>:
Signature-Input: sig=("unencoded-digest";sf);keyid="<pubkey>";tag="ed25519-integrity"
Signature: sig=:<valid_signature>:
An attacker in a MITM position intercepts the request and replaces the script body with malicious JavaScript (e.g., alert(1)), leaving the headers completely unmodified.
The browser receives the response. Network-level signature verification succeeds because the headers are unchanged.
Digest parsing extracts an empty list of digests because sha-384 is unsupported.
Blink's CheckUnencodedDigests receives the empty list, returns true, and skips body validation.
The malicious script is executed, resulting in Cross-Site Scripting (XSS).
Recommendation
If an Unencoded-Digest header is required for signature validation, the system should fail closed if no supported digests can be extracted from it.

Either MaybeBlockResponseForSRIMessageSignature or ParseUnencodedDigestsFromHeaders should be updated to ensure that if the unencoded-digest component is covered by the signature, the resulting list of extracted, supported digests is non-empty. Alternatively, SubresourceIntegrity::CheckUnencodedDigests could be modified to fail if the unencoded_digests vector is empty but a signature validation was performed.

Project Fortify, an experimental security project, has identified the following POC. Please share feedback on issues or improvements on this report to vmiura@

POC: Signature-based SRI fail-open on unrecognized Unencoded-Digest algorithm
Strategy: web-content Bug class: CWE-347 (improper verification of cryptographic signature) — logic bug, fail-open ASAN Error: none (not a memory-safety bug)

When a <script integrity="ed25519-<key>"> resource is served with a valid Ed25519 Signature over an Unencoded-Digest header that uses an algorithm Chrome does not whitelist for body verification (e.g. sha-384), the body is never hashed and the script executes regardless of its content.

services/network/public/cpp/sri_message_signatures.cc ConstructSignatureBase() happily serializes any well-formed structured-field dictionary into the Ed25519 signature base, so the signature verifies.
services/network/public/cpp/unencoded_digests.cc ParseUnencodedDigestsFromHeaders() whitelists only sha-256/sha-512; sha-384 falls into the else { …; continue; } branch and the returned digest list is empty.
third_party/blink/renderer/platform/loader/subresource_integrity.cc CheckUnencodedDigests() returns true for an empty list (explicit code comment).
A MITM/CDN that observes one legitimately-signed response carrying Unencoded-Digest: sha-384=… can replay those headers verbatim with an arbitrary body and bypass integrity="ed25519-…".

Prerequisites
Chromium ASAN build at /chromium/chromium/src/out/asan/chrome (any desktop build works — this is a logic bug, not memory corruption).
Python 3 (stdlib only).
Reproduction
# 1. Start the POC server (pick any free port, here 9001).
cd /poc-artifacts
python3 server.py 9001 &

# 2. Launch Chrome.
rm -rf /tmp/chrome-poc-profile
/chromium/chromium/src/out/asan/chrome \
    --headless --disable-gpu \
    --no-first-run --no-default-browser-check \
    --enable-logging=stderr --v=0 \
    --user-data-dir=/tmp/chrome-poc-profile \
    http://127.0.0.1:9001/ 2>&1 | grep -E 'CONSOLE|unencoded-digest'
(Drop --headless --disable-gpu to see the result table rendered in a real window.)

Expected Result
The page loads three scripts, all with integrity="ed25519-11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=" and all carrying a valid Ed25519 signature over their Unencoded-Digest header:

endpoint	Unencoded-Digest	body matches digest?	correct behaviour	observed
/bug.js	sha-384=:QUFB…: (unsupported)	no	block	EXECUTES ← bug

/control-pass.js	sha-256=:mlu+…: (correct hash)	yes	execute	executes ✔
/bug.js and /control-block.js are byte-for-byte the same situation except for the algorithm token. The former executes, the latter is blocked.

so the server has no third-party dependencies.
