# Description
Descriptionma...@erfurkan.com created issue #1
Feb 10, 2026 08:39PM
VULNERABILITY DETAILS
The WasmTrustedInstanceData object stores data segment start addresses in a FixedAddressArray (a ByteArray subtype) that lives inside the V8 sandbox. This ByteArray contains raw 64-bit pointers to NativeModule wire bytes that reside outside the sandbox in trusted memory. An attacker with an in-sandbox write primitive can overwrite these raw addresses to point to arbitrary memory locations outside the sandbox.

Four code paths dereference the corrupted addresses via memcpy, reading from attacker-controlled out-of-sandbox locations: (1) memory_init_wrapper at wasm-external-refs.cc:738 — handles memory.init instructions; (2) Runtime_WasmArrayNewSegment — handles array.new_data instructions; (3) Runtime_WasmArrayInitSegment — handles array.init_data instructions; (4) Runtime_WasmStringNewSegmentWtf8 — handles string.new_utf8 instructions.

VERSION
Chrome Version: 146.0.7658.0 (dev)
Operating System: Linux x86_64
REPRODUCTION CASE
Run:
d8 --sandbox-testing --expose-gc poc.js
Expected output:
## V8 sandbox violation detected! 
Received signal 11 SEGV_MAPERR 041414141000
The sandbox violation triggers with an OOB read.

when running without asan, I get a different stack trace, matching the EffectiveAddress(trusted_data, mem_index, dst) error from comment #1.

What I observe is that we're trying to memcpy from some memory to an in-sandbox memory. The address of the src buffer is corrupted, resulting in a crash since the corrupted address is inaccessible. In any case, this will at most corrupt the in-sandbox destination buffer, and given that the sandbox is already corrupted, a crash here is working as intended.

The corrupted address is held in WasmTrustedInstanceData::data_segment_starts() which seems to hold a full pointer (Address). Clemens, do you think we can hold a compressed pointer instead? I don't think it would avoid the crash, but it's generally better to not hold full pointers inside the sandbox. Feel free to close this issue if there's nothing to do here.

cl...@chromium.org<cl...@chromium.org> #12Feb 12, 2026 11:42PM
My first assessment is that this whole design of the data_segment_starts doesn't make a lot of sense. We take raw pointers into the wire bytes and store them in an on-heap array of addresses (see WasmTrustedInstanceData::InitDataSegmentArrays). We could instead just store offsets from the wire bytes start.

This design is from before the introduction of the sandbox, and it looks like nobody looked at this yet.

I'll try to completely refactor this, either tomorrow or after my vacation (I'm OOO next week).

[wasm] Refactor storage of data segments in instance

Expand for full commit details
     
    Move from a `FixedAddressArray` plus `FixedUInt32Array` (stored in the 
    sandbox) to a `TrustedPodArray<WireBytesRef>`. 
    Storing absolute addresses in the sandbox is not a good idea anyway. The 
    new design makes the instance smaller, keeps related data closer 
    together and generally improves ergonomics when creating or using the 
    `data_segments` array. 
     
    Drive-by: Use a few more `base::Vector` to pass around views into the 
    wire bytes.

    > `data_segments` array.
