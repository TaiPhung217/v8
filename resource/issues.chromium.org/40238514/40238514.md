Since on-heap metadata is vulnerable to arbitrary concurrent write access, we would create an off-heap shadow GigaCage, which contains writable shadow metadata, and make the on-heap real metadata to read-only instead.

      must not change any behaviors tested by base_tests, it doesn't
      affect base_unittests (except performance changes).

[PA] Make EnableShadowMetadata() and PartitionDirectMap() exclusive

Expand for full commit details
[PA] Make EnableShadowMetadata() and PartitionDirectMap() exclusive 
 
PartitionDirectMap() unlocks PartitionRoot's lock for performance. 
However EnableShadowMetadata() relies on PartitionRoot's lock. So 
While running PartitionDirectMap() in some thread, 
EnableShadowMetadata() may be run in another thread. 
So PartitionDirectMap() metadata will be broken. 
 
To avoid the issue, we added SharedMutex which works like 
std::shared_mutex and used shared lock for PartitionDirectMap and 
unique_lock for EnableShadowMetadata(). 
The reason why we don't use std::shared_mutex is that it allocates 
memory. To avoid memory allocation while memory allocation, we 
need another shared mutex implementation.

Add kConfigurable pools to PartitionAlloc's ShadowMetadata feature.

Expand for full commit details
Add kConfigurable pools to PartitionAlloc's ShadowMetadata feature. 
 
This enables the kConfigurable pool which V8 uses as the pool backing 
ArrayBuffers (See //gin/array_buffer.h). ArrayBuffers give V8 powerful 
primitives to access memory and the V8 sandbox wishes to restrict the 
ability for javascript to escape a certain sandboxed memory partition. 
 
To do this we need to prevent writing and corrupting the Metadata used 
by PartitionAlloc. This is what the ShadowMetadata feature does by 
creating a ReadOnly mapped memory location to allow performant but read 
only access. 
 
ShadowMetadata isn't currently enabled by default and is only on linux, 
but is being tested in pre-stable channels so adding this will mean that 
for some devices this will enable in Canary/Dev.
